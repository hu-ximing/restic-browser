# `rustic_core` 迁移方案

## 决策状态

**已决定但尚未实现。** 当前生产代码仍完全使用外部 restic CLI 读取仓库；`Cargo.toml`
中没有 `rustic_core` 依赖。本方案应在独立功能分支中验证，不能把实验结果描述为 v0.1
现状。

## 为什么考虑迁移

当前每次列目录、搜索、预览或导出都会启动新的 restic 进程。即使启用 restic 缓存，每个
进程仍需重新打开并解锁仓库。这是未缓存目录常见 0.5–0.8 秒延迟的主要来源。

`rustic_core` 可以在应用进程中打开仓库并持有解锁后的 Repository 状态。若兼容性验证
成立，目录读取可以复用同一会话，从根本上避免每次导航的进程启动和 scrypt 解锁成本，
并减少密码经子进程环境传递。

这次迁移不以增加备份或管理功能为目的，也不改变产品交互范围。

## 项目身份和兼容性边界

[`rustic_core`](https://github.com/rustic-rs/rustic_core) 是 `rustic-rs` 社区维护的
第三方纯 Rust 实现。它根据公开的
[restic repository design](https://github.com/restic/restic/blob/master/doc/design.rst)
读写 restic 仓库格式：

- 它不是 restic 项目提供的官方 SDK。
- 它不是对 restic Go 代码的绑定，也不会嵌入 restic 可执行文件。
- restic 仓库格式是兼容依据，但两项目之间没有官方 API 兼容保证。
- 项目 README 明确说明其仍处于早期开发阶段，API 可能在后续版本变化。
- `rustic_core::Repository` 同时提供读取和修改仓库的方法；restic-browser 必须在自己的
  边界中只暴露读取能力，不能因为库可写就扩大产品权限。

## 必须保持不变的边界

迁移只替换仓库读取实现，以下内容保持稳定：

- `Snapshot`、`FileEntry`、`SearchResult` 等应用领域模型及其语义。
- TUI 布局、键位、取消行为和用户可见错误类别。
- 一次运行输入一次密码，密码不持久化。
- 快照倒序、逐层目录浏览、当前快照搜索、预览和单文件无覆盖导出。
- 2 MiB 文本上限、512 MiB 媒体源上限和会话临时目录策略。
- ffmpeg/ffprobe 仍只处理本地临时文件。
- 生产能力仅限读仓库；不得调用 init、backup、save、delete、repair、rewrite、copy
  等修改 API。
- Windows、Linux、macOS 的路径和 Unicode 行为不能退化。

当前 `PreviewService` 和 `ExportService` 直接依赖具体的 `ResticClient`。迁移期间应将
“列快照、列目录、搜索、读取文件”整理为 backend-neutral 的内部读取契约，让 CLI 与
`rustic_core` 适配器返回相同领域类型；不要让 TUI 直接依赖 `rustic_core` 类型。

## 分阶段迁移

### 第一阶段：兼容性探针

第一阶段**只验证**以下能力，不接管默认 TUI，不实现搜索、媒体预览或最终导出流程：

1. 打开 restic 0.19.x 创建的本地仓库。
2. 输入一次密码并只解锁一次，保持会话对象。
3. 列出快照并映射为现有 `Snapshot`。
4. 列出指定快照的一个目录层级并映射为现有 `FileEntry`。
5. 读取一个文件并与 `restic dump` 做逐字节比较。
6. 正确处理中文、空格和 Emoji 路径。

探针应位于独立模块或测试工具中，并在操作前后检查仓库没有意外的持久修改。允许应用本地
缓存写入，但必须识别并记录库是否会创建仓库锁或其他临时对象。

第一阶段通过后才继续；失败时保留现有 CLI 后端，不为迁移改动 TUI。

### 第二阶段：读取后端抽象

- 从当前 `ResticClient` 的四项语义抽取最小只读契约。
- 保留 CLI 实现作为默认后端和行为基准。
- 增加 `rustic_core` 实现，仅通过只读包装层访问。
- 统一认证、仓库不存在、格式不兼容、IO 和取消错误到现有 `AppError`。
- 对可能阻塞 Tokio 的库调用使用受控的 blocking 任务，不阻塞 TUI 事件循环。

### 第三阶段：功能对齐

- 对齐快照排序和元数据。
- 对齐目录的直接子项、文件类型、符号链接、时间、权限和路径规则。
- 明确并实现与 restic pattern 相容的当前快照搜索语义。
- 让预览和导出通过同一个只读“读取文件”接口工作。
- 保持取消后不留下临时文件；确认库级读取能安全停止或被隔离。

### 第四阶段：受控切换

- 在相同测试仓库上并行比较 CLI 与 `rustic_core` 结果。
- 只有在兼容性、性能、内存和跨平台门槛全部通过后，才把 `rustic_core` 设为默认。
- 暂时保留 CLI 后端作为对照和显式回退；`--restic` 在此期间仍有意义。
- README 和 CLI 帮助必须清楚说明当前默认后端及外部依赖变化。

### 未来决策

是否最终删除 CLI 后端、支持远程 backend 或增加目录缓存，不由本迁移自动决定。它们需要
独立证据和产品决策。

## 主要风险及控制

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 格式兼容差异 | 某些 restic 0.19.x 仓库、压缩或格式版本无法读取 | 用 restic 创建格式 v1/v2 夹具，逐项与 CLI 对照 |
| 第三方 API 不稳定 | 升级导致编译失败或语义变化 | 固定精确版本并提交 lockfile；升级单独评审 |
| 可写 API 误用 | 破坏只读产品承诺 | 私有适配器只暴露读取契约；依赖调用审查和仓库不变性测试 |
| 索引内存过大 | 大仓库启动慢或占用过高 | 测量不同索引模式；设置基准和上限，不默认加载完整文件树 |
| 同步/阻塞调用 | TUI 卡顿，取消不及时 | 放入受控 blocking 任务，测量取消和退出 |
| 搜索语义不一致 | 同一 pattern 返回不同结果 | 建立 CLI 金样对照，未对齐前继续走 CLI |
| 路径差异 | Windows 分隔符、非 UTF-8 本地路径或 Unicode 名称异常 | 仓库路径统一语义，本地路径保留 `OsString`，三平台测试 |
| MSRV/构建变化 | CI 或发布工具链突然失效 | 固定 Rust 工具链策略，在三平台先编译再切换默认 |
| 并发和锁行为 | 与 restic 同时读取/备份时冲突 | 测试并发读取，记录锁与本地缓存副作用 |

## 测试矩阵

| 维度 | 最低覆盖 |
| --- | --- |
| 操作系统 | Windows x64、Linux x64、macOS；默认切换前均需通过 |
| restic | 正式支持的 0.19.x；由 restic CLI 创建夹具 |
| 仓库格式 | v1、v2/压缩仓库 |
| 路径 | ASCII、中文、空格、Emoji、深层路径和长名称 |
| 目录形态 | 空目录、深目录、单层数千项目、较大快照 |
| 文件类型 | 空文件、文本、JPEG/PNG、短视频、符号链接（平台允许时） |
| 认证/错误 | 正确密码、错误密码、缺失仓库、不支持格式、损坏对象 |
| 一致性 | 快照字段、目录条目、搜索结果和读取字节与 CLI 对照 |
| 性能 | 冷/热启动、首次/重复目录、CPU、峰值内存和取消耗时 |
| 安全 | 密码不落盘/日志；无意外持久仓库修改；只读 API 审查 |
| 生命周期 | 取消、快速切换目录、退出和异常后无后台任务或预览临时文件 |

当前真实仓库集成测试会在 restic 0.19.x 可用时创建包含中文/Emoji、图片和视频的夹具；
迁移测试应复用并扩充该夹具，而不是另建不一致的测试体系。

## 完成条件

### 第一阶段完成

- 六项探针能力全部通过，并与 restic CLI 结果一致。
- 同一进程中只打开/解锁一次仓库。
- Windows、Linux、macOS 至少完成编译和本地仓库读取验证。
- 未发现意外的持久仓库修改。
- 记录冷/热目录延迟、CPU 和峰值内存，证明继续迁移有收益且资源可接受。

### 整体迁移完成

- TUI 的浏览、搜索、预览、导出和错误行为不因默认后端变化而退化。
- 现有单元测试和真实仓库集成测试对新后端全部通过。
- CLI/`rustic_core` 对照矩阵通过，中文和 Emoji 路径逐字节读取一致。
- 大目录和较大仓库不触发无界内存增长。
- 取消与退出不遗留任务、子进程或应用临时文件。
- 只读审查通过，密码、日志和临时文件约束保持成立。
- `rustic_core` 成为默认后，CLI 回退仍经过自动化测试并有清楚的用户说明。
